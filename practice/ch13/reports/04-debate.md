# Agent Debate 紀錄：priority 不合法時的處理方式

## 爭議決策
- **方案 X（受審）**：priority 不合法（None、"1"、1.0、bool、負數…）時，`add()` 與 `sorted_items()` 靜默改成預設值 3 並繼續執行。
- 方案 Y（對照）：`add()` 嚴格驗證，不合法就拋 ValueError；JSON 載入的壞資料在 `sorted_items()` 時拋 ValueError 並附 id。
- 來源：審查 agent 的 MUST_FIX #1（reports/03-review.md）。

## 裁決規則
3 位審查者平行獨立判斷（彼此看不到對方的意見），**≥ 2 票反對就打回**方案 X。

## 各審查者判斷

| 審查者 | 角度 | 判斷 | 關鍵理由（附實驗） |
| --- | --- | --- | --- |
| R1 | 正確性 | **反對** | 實測 `'1'`、`1.0`、`True`、`-1`、`0` 全部變成 3，使用者要最高優先卻被排到中段；`isinstance(True, int)` 為 True，`sorted([True,2,1,False])` → `[False, True, 1, 2]`；壞值會被 `save()` 永久寫進 JSON，很晚才會被發現 |
| R2 | 安全性 | **反對**（有附帶意見） | 在 `add()` 寫入端靜默修正，等於吞掉呼叫端的 bug 和竄改跡象；`-999` 會插隊排第一、NaN 排序結果無法預期；**但**方案 Y 照原樣在讀取端也有 DoS（一筆壞資料讓整份清單無法顯示）；錯誤訊息用 `{value!r}` 印原值，有 log 污染風險 |
| R3 | 可維護性 | **反對** | 與 `_parse_due`（壞格式就拋錯）不一致，一個模組裡有兩套規則；X 需要為 bool、"1"、1.0、負數各寫特例；先寬鬆、之後改嚴格是破壞性變更，反過來則不是 |

## 結論
- 票數：**反對 3 / 贊成 0 → 方案 X 打回**，採用方案 Y。
- 合議補充（主 agent 整合 R1/R2/R3 的替代建議）：
  1. 新增共用的 `_parse_priority(item)`：None 明確定義為預設值 3（R1、審查 agent 都同意）；bool、非 int、< 1 一律拋 ValueError 並附 id。
  2. `add()` 呼叫它，在寫入端擋下壞值（三位都同意）。
  3. 錯誤訊息只印 id 與型別名稱，不印原值（採納 R2）；`_parse_due` 的訊息一併改掉。
- **少數意見（R2）與處理**：R2 主張讀取端改成 fallback 3 + `logging.warning`，以避免 DoS。這項只有 R2 提出，未達多數，**不採納**，列為已知風險：清單是本機單一使用者的檔案，損毀時「明確報錯並指出 id」比「默默排錯」更好修。若日後清單改成多人共用，再重開這個議題。
