# 練習 02 解答 — 設計一次到位（one-shot）的 prompt

## 使用的 CSV

手邊沒有可公開的真實 CSV，自建一份模擬銷售資料 `fixtures/data/sales.csv`（8 筆，含中文欄位值，故意在 3 列各缺一個數值）：

```csv
order_id,date,product,region,unit_price,quantity,total
1001,2026-09-01,鍵盤,北區,1200,2,2400
1002,2026-09-01,滑鼠,南區,450,3,1350
1003,2026-09-02,螢幕,北區,5600,,5600      ← 缺 quantity
1004,2026-09-03,耳機,中區,,1,1890         ← 缺 unit_price
1005,2026-09-03,鍵盤,南區,1200,1,1200
1006,2026-09-04,滑鼠,東區,450,4,1800
1007,2026-09-05,螢幕,中區,5600,2,         ← 缺 total
1008,2026-09-06,耳機,北區,1890,2,3780
```

手算正解：unit_price 16390÷7 = **2341.43**；quantity 15÷7 = **2.14**；total 18020÷7 = **2574.29**；含缺值的列 = 3。

## 任務 1：一次到位所需的「全部脈絡」清單

| 類別 | 脈絡 | 這份 CSV 的值 | 沒寫會怎樣 |
| --- | --- | --- | --- |
| 路徑 | 輸入檔 | `./data/sales.csv` | Claude 要先找檔 |
| 編碼 | 字元編碼／BOM | UTF-8、無 BOM | 中文在 Windows cp950 下可能亂碼 |
| 格式 | 分隔符、表頭、換行 | 逗號、有表頭、LF | 可能把表頭當資料 |
| 欄位 | 要算哪幾欄 | unit_price, quantity, total | 可能把 order_id 也平均 |
| 欄位 | 其他欄怎麼處理 | 忽略、不轉型 | 中文欄轉數字報錯 |
| 缺值 | 缺值長怎樣 | 空字串或只有空白 | 不知道 `NA`、`0` 算不算 |
| 缺值 | 逐欄略過還是整列丟掉 | **逐欄** | 整列丟掉會得到不同平均（本資料會變成 5 筆） |
| 缺值 | 「跳過幾列」的定義 | 任一數值欄為空即算一列，另列各欄略過數 | 書上骨架這句有歧義 |
| 異常 | 非數字字串 | 視為缺值並警告列號 | 程式直接崩潰 |
| 計算 | 四捨五入規則 | 2 位、ROUND_HALF_UP、固定顯示 2 位 | Python `round` 是銀行家捨入 |
| 輸出 | 位置、目錄不存在時 | `./out/summary.md`，自動建立 | 寫到別處或報錯 |
| 輸出 | 表格格式 | 標題＋三欄表、欄位順序固定、數字靠右 | 格式每次不同，無法自動比對 |
| 輸出 | 終端要印什麼 | 固定三行文字 | 每次措辭不同 |
| 限制 | 可用工具 | 只用標準函式庫，不裝套件 | 可能去 `pip install pandas` |
| 驗收 | 成功標準 | 合法 GFM、與手算一致、要求自行交叉核對並回報 | 只說「完成了」沒有證據 |
| 互動 | 是否允許反問 | 不反問，未涵蓋細節照規則 | 停下來等人 |

## 任務 2：完整 one-shot prompt 與實跑結果

完整 prompt：`prompts/ex02-oneshot.txt`（就是把上表每一列寫成一句話）。另外把書上的原始骨架 `prompts/ex02-book-skeleton.txt` 也跑一次當對照組。

| 中途追問 | 0 | 0 |

| GFM 表格合法 | ✅ | ✅ |
| 輸出格式符合我指定的版型 | 無版型可比（兩欄、無標題） | ✅ 標題＋三欄＋靠右對齊 |
| 「跳過幾列」的解讀 | 自己決定：至少一欄缺值的列數＋各欄缺值數 | 照定義輸出 |
| 程式放哪 | 自己決定放根目錄 `analyze_sales.py` | 照指定 `out/summarize.py` |
| 程式可重跑 | ✅ | ✅（已重跑，輸出一致） |

**結論：兩版都一次成功，沒有缺脈絡導致失敗。** 差別在「可預測性」：骨架版在 3 個沒寫清楚的地方（「跳過幾列」定義、程式位置、表格版型）都是 Claude 自己決定，這次剛好合理，但換一次執行可能就不同；強化版把這些都鎖死，產物可以直接用腳本比對。強化版多花約 6 秒、US$0.03，換到的是 Claude 主動交叉核對並回報驗證結果。

若要說「缺了哪個脈絡」：書上骨架的「跳過幾列缺值」與「缺值略過」放在一起有歧義（是逐欄略過，還是整列跳過？）——這次 Claude 判斷對了（逐欄），但如果它選了整列跳過，平均值會全部算錯。

## 延伸思考：什麼時候「一次到位」反而比「分步互動」差？

一次到位的前提是**你在動手前就知道全部脈絡**。以下情況做不到，硬寫 one-shot 反而浪費：

1. **資料長怎樣還不知道**：例如第一次拿到別部門給的感測器匯出檔，不確定欄位名稱、缺值是用空白、`NA` 還是 `998` 這種故障碼表示。此時先讓 Claude「讀前 20 列、列出欄位與異常值」，看完再決定規則，比憑空寫一個完整 prompt 準。用錯的假設寫 one-shot，Claude 會很有把握地交出一份錯的報表。
2. **需求本身還在探索**：例如要做週報圖表，自己也不確定要看平均還是中位數、要不要分區。先跑一版看結果，再調整，比事先寫死規格省事。
3. **任務很長、中間有不可逆動作**：例如要批次改名上百個檔或寫入資料庫，分步做、每步確認，出錯成本較低。
4. **寫 prompt 的時間比任務本身還長**：一次性的小任務，寫一句話再看結果修一次就好。

工作上的例子：分析場域 PM2.5 資料時，`998` 是感測器故障信號而不是真實數值。如果沒先分步探索資料就直接寫 one-shot「算每個場域的平均 PM2.5」，平均值會被 998 拉高，而且 Claude 不會反問。這種情況應該先分步看資料分佈、確認異常值規則，再把規則寫進 one-shot prompt 交給 Claude 重複執行。
