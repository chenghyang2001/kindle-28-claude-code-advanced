# 練習 02 解答 — 設計壓縮必留清單

> 實際生效的版本寫在專案根目錄 `./CLAUDE.md` 的「Compact Instructions」段落（沒有改全域 `~/.claude/`）。

## 任務 1：壓縮後一定要保留的資訊（7 類）

| # | 類別 | 我工作裡的實例 | 為什麼丟了會出事 |
| --- | ------ | ---------------- | ------------------ |
| 1 | 進行中任務的當前步驟＋下一步 | 「ex01 已完成，正在寫 ex02，接著寫 NOTES.md 再 commit」 | 壓縮後會重做已完成的步驟，或跳過還沒做的步驟 |
| 2 | 關鍵 ID | `claude -p` 的 session_id（`4fd8670e-…`、`87d04814-…`）、git commit hash、背景 task ID、NotebookLM notebook_id | ID 無法從脈絡推回來，丟了就要重查或重跑 |
| 3 | 已修改／新建檔案的路徑（含已 staged 未 commit 的） | `answer/ex01-answer.md`、`scripts/rot-experiment.sh`、`rot-lab/out/` | 不知道改過哪些檔，commit 時會漏檔或多 commit 檔案 |
| 4 | 重要決策與使用者明確偏好 | 全程繁中、快速模式、不 push、不改全域設定、`claude -p` 前清 `CLAUDE*` 環境變數 | 違反使用者偏好最傷信任，而且這些偏好無法從程式碼看出來 |
| 5 | 驗證過的事實與數字（ground truth） | log-1 的 E404=43、log-2 的 E202=52 | 練習 01 症狀 2：沒驗證過的數字會在壓縮後被當成真相 |
| 6 | 等待中的背景任務 | 背景 task ID、預計完成時間、完成後要做什麼 | 壓縮後會忘記去收結果，或重複啟動同一個任務 |
| 7 | 未解決的錯誤＋已試過的解法 | 「Read 讀大檔被截斷 → 改用 Grep」 | 會重踩同一個坑 |

**刻意不保留**：檔案內容原文、大段工具輸出（log、diff）。理由是練習 01 的症狀 1：舊的檔案內容會被誤當成現況，壓縮後一律重新讀檔。

## 任務 2：壓縮後接續摘要範本

```markdown
## 本 Session 目前狀態（壓縮後接續）
- 任務：<一句話說明在做什麼，和完成的定義>
- 進度：
  - 已完成：<步驟 + 產出檔路徑>
  - 進行中：<目前步驟，做到哪>
- 關鍵 ID：<session_id / commit hash / task id / PR 編號>
- 待辦：
  1. <下一步>
  2. <之後的步驟>
  （注意：檔案內容不保留，需要時重新讀檔）
```

套用到本練習的範例：

```markdown
## 本 Session 目前狀態（壓縮後接續）
- 任務：完成 k28 第 4 章 ex01、ex02，寫 NOTES.md 並 commit（不 push）
- 進度：
  - 已完成：rot 實驗兩輪（logs/rot-run1.jsonl、logs/rot-run2.jsonl）、answer/ex01-answer.md、answer/ex02-answer.md、CLAUDE.md 的 compact 段落、NOTES.md、git commit
  - 進行中：等教練下 /compact 後驗證
- 關鍵 ID：實驗 session 4fd8670e-…（run1，被污染）、87d04814-…（run2，乾淨）；commit <hash>
- 待辦：
  1. 壓縮後依 CLAUDE.md 範本自我摘要
  2. 抽查 3 個關鍵事實（commit hash、run2 的 T04 錯誤、port 8080→9090）是否還在
```

## 延伸思考：為什麼 context 越長，品質常常越差？

1. **注意力被稀釋**：模型要在幾十萬個 token 裡找出相關的那幾行。雜訊越多，真正重要的指令和事實佔的比重越小。
2. **舊資訊不會自己失效**：context 裡同時有「舊版檔案內容」和「新版事實」，模型分不出哪個比較新，常常拿舊的來答。
3. **錯誤會累積**：早期一個錯誤結論會被後面的回合當成前提（練習 01 的 T06「沒有重新計算」），越長的 session 錯得越深。
4. **空間被擠壓**：context 快滿時，工具輸出會被截斷，模型只看到一部分資料就下結論。

**我遇過的例子（本次實測）**：Run 2 第 4 回合統計 log-1 時，把 E404 和 E505 的次數對調了（43 和 38）。它用「加總等於 ERROR 總數」自我核對，結果照樣通過。另外，Run 1 塞了兩份大 log 後，第 5 回合的 Read 只讀回 484／1801 行。這兩件事都說明，context 越塞越滿不會讓模型更懂，反而讓它更容易漏看或記錯細節。
