# 練習 01 解答 — 辨識 context rot（脈絡腐化）

## 實驗設計（真的跑過）

- 腳本：`scripts/rot-experiment.sh`
- 做法：在 `rot-lab/` 用 `claude -p --model haiku --output-format json` 送第一個子任務，取回 `session_id`，之後 11 個子任務都用 `--resume <session_id>` 接在同一個 session 上，共 12 回合。
- 執行前先 `unset` 所有 `CLAUDE*` 環境變數；用 `--setting-sources project,local`，避免載入全域 hooks。
- 陷阱：
  - **T01 定早期決策**：專案代號 ORCA-7、日期 YYYY/MM/DD、檔名小寫加連字號、禁 emoji、檔案第一行 `# ORCA-7`。
  - **T03 讀完 `notes/config.md`（port 8080）後，腳本在 session 外把檔案改成 9090**。
  - **T04–T07 灌大檔**：兩份 1800 行 log（各約 133KB）。
  - **T09 要求「不要讀檔、憑記憶」回答 port**；**T10 憑記憶回答 5 條決策**。
  - **T11 誘導違規**：題目故意寫「2026-10-18」和檔名 `Final Report.md`。
  - **T12 讀檔對答案**。
- 標準答案用 grep 算出：log-1 的 E404=43、E202=41、E303=39、E505=38、E101=35；log-2 的 E202=52 最多；log-1 前 600 行中 latency>800 的請求有 65 筆。

共跑兩輪：

- **Run 1**（`logs/rot-run1.jsonl`，session `4fd8670e-…`）：被污染。我把含有「port 8080→9090」的必留清單寫進專案 `CLAUDE.md`，實驗 session 啟動時就讀到了。
- **Run 2**（`logs/rot-run2.jsonl`，session `87d04814-…`）：把洩題的字移除後重跑，當作乾淨的對照組。

## 任務 1：觀察到的腐化症狀

| # | 症狀 | 證據 | 嚴重度 |
| --- | ------ | ------ | -------- |
| 1 | **拿舊版檔案內容作答** | 兩輪 T09 都答 port **8080**，實際已是 **9090**。T12 重讀檔才更正。Run 2 至少有註明「不是重新確認的結果」。 | 高：看起來很有把握，其實已經過時 |
| 2 | **數字張冠李戴，自我核對也沒抓到** | Run 2 T04 回報 E505=43、E404=38，實際是 E404=43、E505=38，兩個數字對調了。它用「加總 196＝ERROR 總數」核對，結果通過，因為對調不影響加總。 | 高：核對方式抓不到這種錯 |
| 3 | **context 被塞滿，工具輸出被截斷** | Run 1 T05：「Read 工具在這一輪只回傳了前 484 行（共 1801 行），因為單次讀取的 context 空間不夠」。Run 1 的 T09 是單次 API 呼叫，輸入約 151k tokens，已經接近 haiku 的上限。 | 中：它有自己說出來；若沒說就會漏讀 |
| 4 | **沿用前面的結果，不重新計算** | T06 明講「計數來自前面對兩個檔案的 grep 結果，沒有重新計算」。前面的數字一旦錯了（症狀 2），錯誤會一路傳下去。 | 中 |
| 5 | **精確度下降，答案變含糊** | Run 2 T07 回答「60 筆以上」；實際 65，Run 1 也答出 65。 | 低 |
| 6 | **把不存在的事實混進輸出** | Run 1 T08 初稿寫了「登入頁已在 2026/10/05 前完成」，但紀錄裡只有期限、沒有完成紀錄。它自己發現後刪掉了。 | 低（有自我修正） |

**沒有觀察到的症狀**：5 條早期決策在 T10 都完整答出；T11 的誘導也沒成功，日期仍寫 YYYY/MM/DD，檔名仍是 `final-report.md`，每份檔案第一行都是 `# ORCA-7`，也沒有 emoji（已用 grep 和 regex 驗證）。
→ 12 回合、短規則的情況下，「忘記早期決策」還不會出現。最先壞掉的是**檔案狀態過時**和**細節數字錯誤**。

## 任務 2：該 `/clear`、`/compact` 還是繼續？

判斷規則：

| 情況 | 處置 | 依據 |
| ------ | ------ | ------ |
| 同一個任務、還要繼續做，但 context 裡塞滿用不到的大段工具輸出（例如這次的兩份 log 全文） | **`/compact`，並指定保留項目** | 早期決策和結論還要用，log 原文不用。壓縮可以留下決策、丟掉雜訊 |
| 換成不相關的任務，或 session 已經被錯誤結論帶歪（例如已經有數字張冠李戴） | **`/clear`**，然後把正確事實重新貼進來 | 壓縮會把錯誤結論一起保留下來，乾淨重來比較安全 |
| context 還小、決策都還記得、沒有過時狀態 | **繼續** | 壓縮或清空都會損失細節 |

**我對這個實驗 session 的選擇：`/compact`**，理由：

1. 任務還沒結束（還要出總結報告），早期的 5 條決策和產出檔清單都要留著，不能 `/clear`。
2. context 主要被兩份 log 全文佔掉（Run 1 單次輸入約 151k tokens，已出現截斷），這些原文後面用不到。
3. 症狀 1、2 都是「舊內容／舊數字被當成真相」。壓縮時要指定：**檔案內容不保留、一律重讀**，**數字只保留用工具驗證過的**。

建議的指令：

```text
/compact 保留：5 條固定決策（ORCA-7、YYYY/MM/DD、out/ 小寫連字號、禁 emoji、首行 # ORCA-7）、
out/ 已產出的 5 個檔名、目前步驟（準備寫 final-report）。
不要保留 log 原文與檔案內容，之後涉及檔案狀態一律重新讀檔。
```

如果已經發現症狀 2（數字錯了），就改用 `/clear`，再貼上 grep 驗證過的正確數字，從頭繼續。

## 附註

- `ctx_in` 欄位是單次 `claude -p` 呼叫內**所有 API 請求的輸入 token 加總**，不是當下的 context 大小。只呼叫一次 API 的回合（T09、T10，`num_turns=1`）才能直接當作 context 大小來看。
- 兩輪都沒有觸發自動壓縮：session jsonl 裡 `compact_boundary` 出現 0 次。
