# 練習 01 解答 — 用多步拆解重寫弱 prompt

任務依本章補充縮小成「**CLI 登入模擬**：記憶體帳號表＋註冊／登入＋錯誤碼＋測試」，不建 JWT 服務。
弱／強 prompt 都用 `claude -p --model haiku` 在**兩個乾淨沙盒**（系統暫存區的空資料夾）實跑，並清掉所有 `CLAUDE` 開頭的環境變數，最後用**同一套驗收測試**評分。

| 檔案 | 用途 |
| --- | --- |
| `ex01/prompts/weak.txt` | 弱 prompt |
| `ex01/prompts/strong.txt` | 強 prompt（4 步拆解＋每步驗收＋成功標準） |
| `ex01/run_sandbox.sh` | 建沙盒 → 清環境變數 → 跑 `claude -p` → 把產出複製回 `ex01/runs/<名稱>-<模式>/` |
| `ex01/acceptance/test_acceptance.py` | 共用驗收測試（11 個案例） |
| `ex01/runs/*/` | 每次實跑的 `claude-output.txt`、`meta.txt`（耗時）、`src/`（產出程式） |
| `ex01/acceptance-results-v1.txt`、`-v2.txt` | 驗收結果原始輸出 |

## 任務 1：弱 prompt 與它的 3 個弱點

```text
做一個 CLI 使用者登入系統
```

（這就是題目「做一個使用者登入系統」縮小到本章範圍的版本，也是我平常最常隨手丟出的那種一句話需求。）

| # | 弱點 | 實跑時造成的後果 |
| --- | --- | --- |
| 1 | **沒有範圍與限制**：沒說資料存哪、要哪些功能、能不能用第三方套件 | haiku 自己決定存成家目錄的 JSON 檔、加了登出／改密碼、做成互動選單，範圍和需求不一樣 |
| 2 | **沒有介面契約與錯誤碼**：沒定義函式名稱、回傳值、錯誤怎麼表示 | 產出用 `UserStore` 和例外（`AuthError`），沒有錯誤碼；外部驗收測試完全接不上（0/11） |
| 3 | **沒有可驗收的成功標準**：沒說怎樣才算完成、要怎麼測 | AI 自己寫的 15 個測試全綠，就宣稱完成；但 CLI 用 `getpass` 讀密碼，stdin 管線餵不進去，它自己也承認「沒有在互動終端機測過」 |

附帶第 4 點：**沒有拆步驟**，AI 一次寫完再回頭測，中間沒有檢查點。

## 任務 2：改寫成多步拆解＋成功標準版

完整內容在 `ex01/prompts/strong.txt`，結構如下：

```text
分 4 步完成，每步完成後自己驗收再進下一步：
步驟 1：資料結構 —— auth.py 的 AuthStore，記憶體 dict。驗收：初始沒有帳號。
步驟 2：註冊／登入 —— register/login 回傳字串錯誤碼
        OK / E_EMPTY_FIELD / E_WEAK_PASSWORD / E_USER_EXISTS / E_USER_NOT_FOUND / E_WRONG_PASSWORD
        檢查順序：先 E_EMPTY_FIELD。驗收：每個錯誤碼都能觸發。
步驟 3：密碼安全 —— pbkdf2_hmac + 每帳號 os.urandom(16) salt。驗收：屬性中找不到明碼。
步驟 4：CLI + 測試 —— cli.py 逐行讀 stdin「register/login/quit」，每行印一個錯誤碼；
        不認得的指令印 E_BAD_COMMAND；test_auth.py 用 pytest。驗收：pytest -q 全綠。
成功標準：1) 錯誤密碼→E_WRONG_PASSWORD，帳號不存在→E_USER_NOT_FOUND 2) 不存明碼
          3) stdin 餵指令每行一個錯誤碼 4) pytest -q 全綠
不要建 JWT、不要建 web 服務、不要問我問題，直接做完。
```

### 共用驗收測試（11 個案例）

註冊成功、登入成功、錯誤密碼、帳號不存在、重複帳號（不分大小寫）、弱密碼、空欄位 ×3（空字串、全空白、空密碼）、記憶體內沒有明碼、CLI 端對端流程（stdin 餵 5 行指令，檢查輸出與 exit code）。

### 實跑結果

做了兩組實驗。第一組沒有隔離設定，結果發現 `claude -p` 在空沙盒裡**仍會載入使用者全域 `~/.claude/CLAUDE.md`**（裡面有「先問快速模式」「三 agent 鐵律」等規則），干擾很大。第二組加上 `--setting-sources project,local` 隔離（實測：問它「指示裡有沒有提到三 agent 鐵律」，預設回「有」，加參數後回「沒有」）。

| 組別 | 耗時 | 產出 | 自帶測試 | **共用驗收** |
| --- | --- | --- | --- | --- |
| 弱 × 載入全域設定 | 42 秒 | **0 個檔**：反問要用快速模式還是完整模式、要指令版還是選單版，然後停下來 | — | **0/11**（沒東西可測） |
| 強 × 載入全域設定 | > 600 秒 | 3 檔／518 行：走 writer→QA→reviewer，`auth.py` 被退回改 3 輪 | 18 passed | **11/11** |
| **弱 × 乾淨沙盒** | 214 秒 | 3 檔／314 行：JSON 檔存家目錄、互動選單、例外而非錯誤碼 | 15 passed | **0/11**（沒有 `AuthStore`；CLI 卡在選單，exit 130） |
| **強 × 乾淨沙盒** | **93 秒** | 3 檔／298 行：完全照 4 步規格 | 32 passed | **11/11** |

> 驗收測試 v1 的 CLI 案例只取「最後 4 行輸出」，強×乾淨版的 `quit` 會多印一行 `OK` 而被判失敗（10/11）。檢查後判斷這是**我的測試寫太嚴**：規格說「每行指令印一行錯誤碼」，`quit` 也是指令，印 `OK` 合規格。v2 改成檢查前 4 行，並允許 quit 多印一行 `OK`。v1、v2 原始輸出都保留。

### 效果差異結論

1. **一次到位率**：強 prompt 兩組都 11/11；弱 prompt 兩組都 0/11。
2. **「自帶測試全綠」不等於「符合需求」**：弱版自己的 15 個測試全過，但對外部驗收來說毫無用處。成功標準要由**下需求的人**定義，不能交給 AI 自己出題自己考。
3. **速度**：乾淨沙盒下強 prompt 只花 93 秒，比弱 prompt 的 214 秒快一倍以上，因為 AI 不用自己猜範圍、加多餘功能。
4. **成功標準也會有漏洞**：強 prompt 沒規定 `quit` 要不要輸出，兩次實跑就有兩種行為，驗收測試也因此需要修正一次。下次的 prompt 應該補一句「quit 不輸出任何東西」。
5. **環境也是 prompt 的一部分**：全域 CLAUDE.md 會讓弱 prompt 直接停下來反問、讓強 prompt 耗時多好幾倍。做 prompt A/B 測試要先隔離設定，否則比的是設定檔而不是 prompt。
