# 從副駕駛到指揮官：編排決策表

## 核心轉變

| 面向 | 副駕駛（Copilot）心態 | 指揮官（Orchestrator）心態 |
| --- | --- | --- |
| 你的角色 | 跟 AI 一起逐行寫 | 定義目標、切任務、驗收結果 |
| 主要產出 | 程式碼 | 合約（規格／介面）、派工單、驗收標準 |
| 品質來源 | 你盯著每一行 | 自動化驗證（測試、lint、CI）+ 抽查 |
| 瓶頸 | 你的打字與注意力 | 任務切得好不好、合約清不清楚 |
| 失敗模式 | 慢 | 平行打架、脈絡漂移、沒人驗收 |

一句話：**指揮官不衝鋒，只管邊界、合約和驗收。**

## 決策表

| 模式 | 什麼時候用（判斷條件） | 典型例子 | 主要風險 | 降低風險的做法 |
| --- | --- | --- | --- | --- |
| **單一 session** | 任務小（< 1 小時、1～3 個檔案）；步驟有強依賴、必須依序；需要你頻繁判斷或探索中 | 修一個 bug、改一個函式、讀懂一段程式 | context 越拉越長、後期品質下降；你變成瓶頸 | 階段性 `/compact`；每完成一段就 commit；超過 ~8 輪就寫檢查點摘要 |
| **git worktree 平行** | 2+ 個**互相獨立**、會改到**同一批檔案**或要各自跑完整建置/測試的工作；每項都夠大（≥ 30 分鐘），值得各開一個完整 session | 同時做 feature A 與 feature B；一邊重構、一邊修 hotfix | 合併衝突；分支各自飄離主線；磁碟上殘留 worktree 沒清 | 先切乾淨邊界再開；從 `origin/main` 長出；短命分支、做完就 merge + `git worktree remove` |
| **子代理（subagent）** | 主 session 要保持 context 乾淨；子任務能用一段文字講清楚、有明確輸入輸出；可平行且**檔案不重疊** | 平行搜 codebase；一個寫實作、一個寫測試；獨立審查 | 子代理只知道你給的 context，會猜；結果難觀察；平行改同一檔會互蓋 | 先寫合約（SPEC）當唯一依據；明確列「只准改哪些檔」；主 session 整合後自己跑驗證，不信「我測過了」 |
| **GSD／Ralph 自主迴圈** | 目標可被**機器判定完成**（測試全綠、清單全勾）；工作量大且重複；可以無人值守；已有規劃文件（PLAN/PRD） | 依 PRD 逐項實作 20 個小功能；把整個 repo 的型別錯誤清光 | 跑偏或卡在同一錯誤無限重試；燒大量 token；改壞了沒人發現；越權動到不該動的東西 | 設停止條件（最大迭代數、預算上限）；每輪 commit 方便回滾；限縮權限與可改範圍；固定檢查點人工抽查 |

## 快速判斷流程

```text
任務能在一個 session、1 小時內做完？
├─ 是 → 單一 session
└─ 否 → 能拆成彼此獨立的子任務嗎？
        ├─ 否（強依賴）→ 單一 session，分階段 + 檢查點
        └─ 是 → 子任務會改到同一批檔案、或各需完整環境嗎？
                ├─ 是 → git worktree 平行（每個 worktree 一個 session）
                └─ 否 → 子代理（主 session 只派工與整合）
                        └─ 完成條件能自動判定、且量大重複？
                           └─ 是 → 考慮 GSD／Ralph 自主迴圈（加停止條件）
```

## 指揮官的四件事

1. **切**：把任務切成邊界清楚、檔案不重疊的單位。
2. **約**：寫合約（介面、預期值、錯誤行為、禁止事項），讓各代理有同一份依據。
3. **派**：一次派齊可平行的工作，派工單寫清「只准改什麼」「回報什麼」。
4. **驗**：自己跑測試整合，不採信子代理的自述；失敗就帶證據退回。
